# Events

!!! abstract "Grain"
    ONE row per event per production. A multi-day event is ONE row.
    Always the latest known state.

- Built by UPSERT from the newest import session. Never deleted and re-created.
- 🔴 **Upsert key = `TaskID` + `fkProduction`.** A CU event task can carry two shows; each calendar prints its own copy.
- `fkStandardEvent` is the reporting spine: per-production churn on TaskID, season-wide "we never move these" on the standard event.
- Unscheduled (no date) events collect at the top of week one, legacy parity.

## 🔴 SPANS STAY WHOLE (ruled by Fiona, 2026-08-08)

The legacy file DUPLICATED a multi-day event into one record per day (`CREATE_multipleDays`, flagged `autoGenerated = 1`) so that a day-portal could find it. **That is killed.**

**Why it cannot survive:**

1. **It breaks the upsert key.** Three rows with an identical `TaskID` + `fkProduction` means the second import cannot tell an update from a duplicate. Either the key grows a date and stops being an identity, or re-import returns to delete-and-replace — and the whole history model goes with it.
2. **It destroys the change count.** A span moving Mon–Wed → Tue–Thu is ONE change. Duplicated, it reads as three deletions and three creations, so `WatchHash` counts noise on exactly the events that move most.
3. ⭐ **`autoGenerated` is the tell.** A flag meaning *this row is not real* is the schema saying the row should not exist. Same species as a convenience-copy date or a second-claimant field.
4. **The agenda gets correct for free.** A span appears ONCE with a date range. Under duplication it could not — hence the `autoGenerated` descending sort buried in `Events Agenda View SORT`.

## How a day-portal finds a span

Not an equality on a stamped key. **A multi-predicate RANGE relationship:**

```
WORKDAYS::DATE      >=  EVENTS|span::Start_DATE
WORKDAYS::DATE      <=  EVENTS|span::End_DATE
WORKDAYS::fkCalendar =   EVENTS|span::fkCalendar
```

Every day inside the span sees the event, from ONE stored row. Same pattern as CALENDAR_EMPHASIS — one range-resolution mechanism used twice, not two different tricks.

- 🔴 **`End_DATE` must never be empty.** A single-day event needs `End_DATE = Start_DATE`; empty means `DATE <= ""` and the event vanishes from every portal. Auto-enter it.
- ⚠️ Inequality predicates cannot use a stored index like equality can, so a span portal is slower. On a 68-day grid with ~120 events this is a non-issue.
- 🚪 **Escape hatch, NOT built:** if performance ever bites, generate an `EVENT_DAYS` join (one row per event-day, rebuilt at import, never edited, never the source of truth). That buys duplication's SPEED without its IDENTITY problem. Named here so nobody re-invents `autoGenerated` under pressure.

### Open, from Beckett

- ⬜ **A span crossing a HIDDEN day** renders on both sides of a gap and reads as continuous. Duplication handled this by accident (no row was made for a hidden day). Range joins have no opinion. Decide what the page should show.
- ⬜ **A span running past the calendar bounds** truncates silently — the page understates duration with no marker.
- ⬜ **Visual continuation.** A five-day load-in prints its name in five cells with no "continues" affordance. Legacy had the same problem, so not a regression, but nobody has specified it.
