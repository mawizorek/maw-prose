## URITP People · 2026-10-23

- **D-052** - **`XT_Refresh_Fields` stays a dispatcher: it resolves the container's system and calls that system's `ADAPTER_<System>_RefreshFields`, which is the only script that knows the endpoint and the response shape.** Michael's ruling, 2026-10-23, when the alternative was to fold the single adapter back into the housekeeping script because ClickUp is the only system connected today. Kept split because D-046 already drew this line for the sync path and a second shape would mean the refresh is read one way and the run another. The dispatcher takes a container key or a source name, reads the system through the same `ExecuteSQL` context read `SYNC_Run` uses (D-048 ruling 6), and errors loud on a system with no adapter rather than falling back to ClickUp's shape. The adapter calls `GET /api/v2/list/<list_id>/field` with a bare `Authorization` header, walks the response, and fills `xt_FieldName` and `xt_FieldType` on the container's existing `xt_FIELDS` rows matched on `xt_FieldID`; `mapKey` is typed and never written by a script, and a field in ClickUp with no row here is reported, not created, because a mapKey is a decision. Both scripts are written and in `apps/uritp-people/scripts/`; neither is installed yet, so checkpoint 1 of the sync plan still rests on typed names and types.
- **D-051** - **Every field that picks from a value list carries a foreign key to `VALUES::PrimaryKey`, and the label is snapshotted into a sibling `stored_` field at write time. One mechanism, no literals.** Michael's ruling, 2026-10-23, overriding a proposed split that would have keyed the reconcile Decision relationally and stored the event Action as a literal string. His objection, and it was the right one: two ways to do the same thing is not a standard, and keying to the key is the whole point of the relational value-list pattern this file already runs (`value_LISTS` holding one record per list with its global, `VALUES` holding the members with `fk_List` and `sort_Index`, a filtered `value_LIST_*` occurrence per list on the graph). What he conceded the literal was good for, a log line that still reads after someone renames a value, is solved by copying the resolved label rather than by abandoning the key: the pick writes `fk_`, a `Set Field` immediately after snaps the related `VALUES::Name` into `stored_`, and the log reads with no join and no live dependency. Built as `sync_EVENTS::fk_Action` with `stored_ActionLabel` and `sync_RECONCILE::fk_vDecision` with `stored_DecisionLabel`, against `SYNC_Action` (PULL, PUSH, ADOPT, EXPORT) and `SYNC_DECISION` (PENDING, FM, XT, APPLIED). `stored_` keeps its established meaning, frozen at write; `null_` still marks a nullable field. Letter case on a value is layout formatting and carries no meaning, because nothing matches on the label. The one exception stays D-048 ruling 2, where `status_Person` mirrors ClickUp's status labels one to one: that label is an external contract, not an internal one. The flag that says a list is a status set moved up a grain in the same build, from `VALUES::bool_isStatusList` to `value_LISTS::bool_isStatusSet`, which is where it belongs and is recorded here because nothing else records it.
- **D-050** - **On FileMaker 19 the app catalog matches on base-table NAME and `fm_BaseTableID` is typed once per table from the DDR export. Empty is the worklist.** Michael's ruling, 2026-10-23, after the refresh's first probe returned *"The table named FileMaker_BaseTables does not exist"* in a 19.6.3 file. The fact that forced it: `FileMaker_BaseTables`, `BaseTableNames` and `BaseTableIDs` all arrived in **FileMaker 2023 (20.1)**, not 19.4 as D-043 and the catalog standard both claimed; 19.4.1 added only `FileMaker_BaseTableFields`, which reports base-table names and their fields and no table id; and `FileMaker_Tables.TableId` is a table-occurrence id, the wrong grain. So there is no base-table id to read on 19, and the standard had been written against a system table nobody had ever run. Michael's reasoning for typing the ids rather than waiting on an upgrade: they are static, the set of base tables is finite and changes rarely, and a typed id only ever needs touching when a table is added. The refresh therefore reads `SELECT DISTINCT BaseTableName FROM FileMaker_BaseTableFields`, finds each name in `Target_Tables`, creates a row with an empty `fm_BaseTableID` when it has never seen the table, stamps `isPresent` and `LastSeenAt` on every row it does see, flips `isPresent` to 0 on a row it stops seeing, and closes with a dialog counting the file's base tables, the new rows, the gone rows and the rows still waiting on an id. A find on `isPresent` 1 with an empty id is the seeding worklist, so the manual step is never a guess about which tables are new. **The cost, named rather than hidden: a renamed base table reads as one gone plus one new**, because nothing in a 19 file can match it otherwise; move the id across by hand or reseed from the next DDR. Also: a base table with no fields defined is invisible to `FileMaker_BaseTableFields`, and the conformance gap still computes correctly on 19.4.1, which makes adding an `AuditGap` field worth doing. Amends D-049's mechanism, which assumed an id upsert, and corrects the version floor in D-043 and the catalog standard to 19.4.1. Upgrading to FileMaker 2023 reverses all of it and returns the id to being generated; the standard says so in place. *(Built as `AuditField_gaps`, Michael's name, and all 22 ids were seeded from the DDR the same evening.)*
- **D-049** - **The app catalog's table half is `Target_Tables`, the name URITP People actually built, and D-043's `APP_TABLES` is retired.** Michael's ruling, 2026-10-23, from Manage Database: the table exists as `Target_Tables` carrying `fm_BaseTableID`, `fm_BaseTableName`, `isPresent` and `LastSeenAt`, and APP_TABLES was never created in any solution, so there was nothing to keep compatible and no reason to carry the weaker name forward. The standard follows the file. `APP_CatalogRefresh` was rewritten against the live field set: it writes `fm_BaseTableName`, sets `isPresent` to 1 on every table it sees and to 0 on one it stops seeing, and stamps `LastSeenAt`. Gone-not-deleted survives, by flag instead of by `RemovedTimestamp`, and nothing was lost with the timestamp because `LastSeenAt` already answers when a table was last seen. Installing it needs a layout on an occurrence of the catalog table, named in `$layoutTables`, since the refresh navigates by layout name. Two things this ruling leaves open: `Target_Tables` has no `AuditGap` field, so the refresh computes D-043's conformance gap and discards it; and no file has a layout catalog, so whether it becomes `Target_Layouts` for symmetry or stays `APP_LAYOUTS` has no built name to follow. The standards shelf also still carries a register per catalog table while the app carries its own `Target_Tables.tsv`, which is two registers for one table. Amends D-043's naming only. *(Match key amended the same day by D-050: on FileMaker 19 the upsert is by name, not by id. Installed in URITP People as `refresh | Target_Tables`, and the gap field now exists, so the first open item is closed.)*
- **D-048** - **The six rulings the sync plan held open are settled as recommended, and `SYNC_Run` reads its context in one `ExecuteSQL` join rather than through relationships.** Michael's rulings, ClickUp session of 2026-10-23, in the order the plan listed them. (1) A `sync_EVENTS` row is written only for a new or changed task; logging every unchanged task would write hundreds of identical payloads a pull. (2) `status_Person`'s value list mirrors the ClickUp list's statuses one to one (new, active, circle back, connect with, plus its closed ones), so status needs no translation table and a status added in ClickUp is a value-list edit rather than a script change. (3) The task name is FileMaker's `auto_Name_FirstLast`, which already prefers a preferred name, so the first full push renames every task whose name differs and a sample is checked before it runs. (4) Name as in Playbill is mirrored as `playbill` (`cc4886b9-ed39-4d69-bd97-69fccadcba9e`, short text) against `PEOPLE::stored_NameDisplayInPlaybills`, both ways like everything else under D-047, which makes ten mirrored fields and five calls per person on a full push. (5) The single test PEOPLE record is deleted before the first pull, so the initial load starts from zero. (6) `SYNC_Run` reads its source, its container and its system in one `ExecuteSQL` join with every field name built from `GetFieldName` (D-043), not through relationships from `sync_SOURCES_fxtContainers`: one call, no new table occurrences on a graph that was just rebuilt, and D-043 already removed the rename risk that was the argument against SQL text. Every downstream script receives the same context as variables either way, so the call changed one script. Mechanics in `apps/uritp-people/sync-plan.md`. *(Ruling 4's FileMaker field was renamed `NameDisplay_InPlaybills` in the setup build later that day; ruling 5 is done.)*
- **D-047** - **Every field URITP People mirrors with ClickUp syncs both ways through `sync_RECONCILE`. Nothing is push-only.** Michael's ruling, ClickUp session of 2026-10-23: a push-only field is a broadcast, not a sync, and it silently overwrites a fix made in ClickUp. One rule covers names, pronouns, status, the first two email addresses and the primary phone. Adoption seeds every mirrored field from ClickUp, contacts included. After that each field is compared three ways: FileMaker now, ClickUp now, and the base, the last value both sides agreed on, held in the record's newest `sync_EVENTS` row. An edit made only in FileMaker is pushed; one made only in ClickUp becomes a pending reconcile row; one made on both sides is a conflict row. FileMaker's value stands until a row is decided, and the push skips any field with a pending row. Taking ClickUp's email or phone inserts it and moves the old row down, so no contact is lost. Replaces the baseline's same-day wording that emails and phones were pushed and never pulled back. Mechanics in `apps/uritp-people/sync-plan.md`.
- **D-046** - **URITP People's schema baseline of 2026-10-23 supersedes D-042's design: FileMaker is canonical, ClickUp's PEOPLE list is a mirror and an intake.** The sync layer is generic, not ClickUp-shaped: `xt_SYSTEMS`, `xt_CONTAINERS`, `xt_FIELDS`, `xt_RECORDS` and `XTERNAL_JOINS` hold everything about an outside system; `sync_SOURCES`, `sync_SESSIONS`, `sync_EVENTS` and `sync_RECONCILE` log every run; only `ADAPTER_<System>_` scripts know a system's shape. PEOPLE carries no ClickUp ids; a person meets a task only through a join row, made by adoption. Contacts hang off a `CONTACTS` card owned through one `fk_Owner` (a person, venue, organization, or a production in Production MAWnster), each contact list ordered by `sort_Index` with the first as primary. A payload is stored once, on `sync_EVENTS`. Verified against three schema exports that day. D-042's table notes are in `apps/uritp-people/meta/` marked superseded; its no-cascade-delete rule from a person to their contacts stands.

## This repo · 2026-08-09

- **D-038** — **The menu-mirror depth exemption is not limited to `apps/`.** It applies wherever the extra levels copy an application's own object types, which is why `standards/filemaker/custom-functions/json-params/` is legal at four segments. The test is unchanged and still narrow: could you read every folder name off the application's own menu? Custom functions are a FileMaker object type, so yes. - **D-037** — **Cross-app FileMaker definitions are canonical here, and installed copies audit against them.** A custom function cannot be shared between FileMaker files, so there is no way to keep two installs identical and nothing should pretend otherwise. Instead one definition lives in `standards/filemaker/`, each app holds a pointer rather than a copy, and a conformance fixture beside the definition lets a solution test its own local functions and find out it has drifted. Behaviour is compared, never a version constant: FileMaker cannot read its own function bodies at runtime, so a stamp is a label nobody bumps. Self-audit for now, meaning the app pulls the fixture from this public repo with `Insert from URL` and no credential.
